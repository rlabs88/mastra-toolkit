# Factory Integration Package Context

## Past

Factory construction, authentication, provider preparation, storage, canonical agents, and sandbox selection were coupled through the root source tree.

This package also excluded `dynamic_workflow` and recorded the exclusion as following from the same upstream blocker that keeps canonical modes and native subagents unavailable. That attribution was wrong. The blocker is that `MastraFactoryConfig` in `@mastra/factory@0.5.0` accepts no `modes`, no `subagents`, and no controller-construction callback, so canonical delegation cannot be attached before Factory constructs its one controller. Contributing a tool through `FactoryIntegration.agentTools()` is a different, supported seam, and the workflow methods `dynamic_workflow` needs — `addStoredWorkflow`, `removeWorkflow`, `getStorage` — are public on `Mastra` in `@mastra/core@1.57.0`. The genuine prerequisites were tenant isolation, background-task capacity, and a bounded dispatch allowlist, none of which are upstream concerns.

## Present

This package binds the versioned `ToolkitRuntimeContract` into Mastra Factory without importing MCode. Its four-module facade owns the Factory controller projection, request-local binding, configuration-backed infrastructure, integrations, and the complete Factory/Mastra runtime lifecycle while the application owns signal handling only. Factory retains exactly one upstream-owned controller and one built-in GitHub source-control integration. Optional GitHub Projects V2 configuration requires that canonical GitHub integration, injects the temporary Projects GraphQL credential at the host boundary, and registers the `factory-github-projects` storage domain, verified-webhook observer, and scheduler worker without duplicating webhook verification. The control plane can omit repository execution; enabled repository execution consumes the shared sandbox machine as a fleet template and persists project/user/session bindings. Ephemeral development and persistent operations are explicit, fail-closed runtime profiles. Factory still exposes no modes, subagents, or controller-construction callback, so diagnostics explicitly report canonical delegation as upstream-blocked and the integration exposes neither role-specific delegation tools nor an unsafe neutral adapter.

Durable orchestration is available separately, through the tool seam rather than the controller seam. The projection constructs one `dynamic_workflow` and both attaches it to the canonical agents it registers and contributes it through `agentTools()`. Four host-owned decisions carry its authority. The `authorize` hook requires a persisted Factory project session, an authenticated user, and that session's sandbox-backed workspace; it runs before any action dispatch, so `run`, `resume`, and `inspect` are all gated, and it is what confines the tool to the execution stage without reading governed work-item status from a tool boundary. The `scope` hook supplies the `project-user-session` triple the approval binding already declares, so orchestration is never isolated more loosely than the approvals authorizing it, and it is derived independently of `authorize` so dropping that hook still cannot produce an unscoped id. `resumable` is `false`. The dispatch allowlist is enumerated explicitly rather than derived from the canonical role list.

The two agent lists this package maintains carry deliberately opposite policies, and conflating them would be a regression in both directions. `diagnostics().agents` is derived from what the projection actually registers, because diagnostics describe reality and a literal there is how people come to believe false things about a running system. `FACTORY_DYNAMIC_WORKFLOW_AGENT_IDS` is a hand-maintained literal, because it is a security boundary and the whole value of writing it out is that a fifth canonical role cannot join it by the canonical list merely growing. Ayra sits in it by a deliberate widening rather than by derivation: it authors dynamic workflows on every other host, so excluding it would make Factory the one host where the orchestration role cannot orchestrate.

Tenant isolation is closed for authorization, identity, and discovery. Because the host supplies a scope, the workflow id is content-addressed over the scope as well as the graph, so two projects submitting an identical graph no longer collapse onto one id, one definition row, and one refcounted registration; the stored definition carries a scope digest, so `inspect` lists only the caller's own runs; and a `resume` naming another scope's row is refused with a dedicated mismatch that never echoes the owning scope, so guessing an id reveals nothing. What remains is narrower and is not about tenancy: a dispatched run receives a fresh request context carrying no Factory session, so its steps cannot resolve the project workspace they were authorized against. For a `run` that is bounded, since the graph executes inside the authorizing turn under its abort signal. A suspended run outlives that turn, which is why `resumable` stays `false` — resuming would be the only path where a Factory graph executes against a workspace no live authorization ever validated. `capability.orchestration` records exactly which of these is enforced and which remains residual.

Background-task capacity is a Factory composition decision rather than a shared default. The host policy caps one agent instance at a single background task and rejects the overflow, which serializes one user's work on a single-user host but becomes a per-process cap in Factory, where one agent instance is shared by every project session. Since `dynamic_workflow` may hold a slot for its full ten-minute ceiling, the runtime sizes capacity from `maxSandboxes` — the governor that already bounds concurrent sessions — and degrades an over-capacity enqueue to inline execution instead of failing an unrelated project.

## Future

Factory must mount the shared contract's canonical modes and native subagents once an official upstream construction seam exists, then add request-aware sandbox adapters for the explicitly unsupported repository configuration surfaces. No Mastra fork, dependency patch, second controller, or host-checkout fallback is part of that path. Only after the single-project contract is proven may it scale across isolated projects.

Re-enabling `resume` needs durable request-context reconstruction, so a dispatched run carries the Factory project session it was authorized against rather than a fresh identity. That is the same gap that keeps a started graph's steps from resolving the session workspace, so closing it improves `run` and `resume` together; more scoping would improve neither. Whether Factory's own controller agent or per-project mounted specialists ever join the dispatch allowlist is a separate deliberate decision, and growth of the canonical role set is not one.
